# Этап 2: конечный список проверки и закрытия

Состояние на 2026-09-29: этап **закрыт по согласованному игровому объёму**.
Это итоговый checklist с доказательствами и известными ограничениями;
хронология пакетов находится в `REFACTOR.md`. Новые находки сверять с
границей этапа: визуальное воспроизведение относится к этапам 3–4,
полный поведенческий паритет со Steam — к этапу 7.

## Подтверждённая база

- Windows x64 собирает и запускает `Game.exe`. На Linux x86-64 и ARM64/QEMU
  связан и исполняется headless-`CWorld`, но не графический клиент.
- Имеются прогоны всех 52 активных корней сценариев с партией, собственным
  save/load и продолжением. Строгий wire-аудит 52/52 на полном зеркале
  игровых ресурсов прошёл на Linux Clang x86-64; отдельные регрессии
  боевых и скриптовых путей описаны в диагностике репозитория реконструкции.
- Все 23 `.res` прочитаны побайтно (57 880 записей); при проверке
  эффективных данных нужны также 14 каталогов отдельных ресурсов
  (2 421 файл). Типизированные проверки уже есть для БД, карт, AI,
  анимаций, голов, строений и других выбранных классов; побайтный обход
  пакетов **не** заменяет смысловую проверку каждого используемого типа.
- Windows-пути Unicode и отделение пользовательских сейвов проверены в
  чистых архивах; Linux-слой слотов проверен отдельно. Это не весь
  интерфейс сейвов будущего Linux-клиента.

## Контрольные пункты — выполнять по порядку

1. **Зафиксировать границу игрового ядра.** Сопоставить явный список
   Windows `Main_SRC` с переносимыми Linux-целями, затем для каждого
   отсутствующего модуля установить *реальную* достижимость из игры и
   класс: нужен этапу 2 / платформенный или графический этап / интерфейс
   будущего клиента / этап 7 / неиспользуемая заготовка или редактор.
   В зафиксированном коммите 338 Windows `.cpp`, 155 не перечислены в
   переносимой сборке — это кандидаты для аудита, **не** 155 недостающих
   игровых файлов.
   Результат: таблица решений с вызовом-основанием и тестом для каждого
   включённого игрового модуля. Реально нужные неграфические пробелы
   перенести; не тащить редакторские FaceGen-функции и произвольные моды.
   **Закрыто для текущего набора источников:** все 155 кандидатов, включая
   22 нетипичных исключения, разобраны в
   `../Silent-Storm-Reconstruction/diagnostics/STAGE2-SOURCE-BOUNDARY.md`.
   Среди них не найден живой неграфический модуль мира, который отсутствует
   в Linux-ядре. Старый BSP-коллайдер и счётчик объёма не вызываются;
   игровые геометрия и столкновения используют другие, уже переносимые
   реализации. Если пункт 2 выявит новую живую ссылку, соответствующее
   решение здесь надо пересмотреть.

2. **Закрыть охват оригинальных данных.** Построить граф «игровая ссылка
   из `game.db`/Lua/активного loader → ID ресурса → фактически выбранный
   отдельный файл или пакет → типизированный декодер/тест». Для каждого
   достижимого неграфического типа требовать строгую загрузку, существенные
   значения и одинаковый смысловой результат на Windows x64, Linux
   x86-64 и ARM64; спорные низкоуровневые поля сверять с x86-эталоном.
   Ресурсы только редактора и визуальное воспроизведение не входят.
   Результат: воспроизводимый реестр покрытия и конкретный список/ноль
   непрочитанных реально нужных типов, а не утверждение «все пакеты
   открылись».
   **Закрыто в согласованной границе этапа 2.** Реестр всех 23 семейств с
   исходными точками входа, разрешением отдельных файлов поверх `.res`,
   DB/Lua-корнями и адресными тестами лежит в
   `../Silent-Storm-Reconstruction/diagnostics/STAGE2-DATA-ROOTS.md`.
   Сценарные строения/рельеф, маршруты, коллизии, карты кампании,
   анимации, головы, последовательности и оба типа CPU-геометрии
   проверены по существенным полям на Windows x64, Linux x86-64 и
   ARM64/QEMU. Итоговый аудит выявил ранее пропущенную ветку геометрии
   строений: `NativeBuildingPieceResourceTests` проверяет 2 928 записей,
   связь 814 строительных ID с таблицей `CGeometry` и отсутствие игрового
   ключа к 966 пакетным записям без DB-строки. Имеющиеся 6 780
   DB-связанных потоков `Sequences` декодированы и загружены; для 445
   выбираемых голосовых ID без файла проверен штатный пустой результат.
   Отсутствующий BSP двери 234 и необязательные отсутствующие ресурсы
   не выданы за декодированные. Непокрытых *присутствующих, достижимых
   игрой неграфических CPU-типов* по этому реестру — ноль. Это не
   доказательство всех динамических решений AI/Lua и не перенос
   визуального воспроизведения, света или частиц. Новая исходная
   ссылка вне реестра потребует дополнить аудит. Следом выполнен аудит
   64-битного ABI и файлового контракта.

3. **Закрыть 64-битный ABI и файловый контракт.** Аудировать *весь
   достигнутый в пунктах 1–2 контур* на размеры `long`/Windows-типов,
   указатель→32 бита, x86-ассемблер, host-выравнивание, знак/порядок
   байтов, регистр имён и кодировки. Недавние `CUnitArea::places` и
   `CUnitServer::tDeathTime` показывают, что нулевой raw-аудит сам по
   себе не ловит арифметический тип неправильной ширины. Каждый найденный
   случай получает адресную межплатформенную регрессию, проверку памяти/UB
   и честную отметку о совместимости формата. Результат: проверенный
   отчёт по категориям, а не только поиск по тексту.
   **Выполненные срезы аудита:** (а) игровые слова
   времени/ID и `long`/Windows-типы; (б) указатели, хеши, x86-ассемблер
   и арифметика выравнивания; (в) сериализация и раскладка структур;
   (г) эффективные пути, регистр и кодировки на Windows/Linux;
   (д) межплатформенные регрессии находок и сводный отчёт. Первый
   срез и его воспроизводимые поиски — в
   `../Silent-Storm-Reconstruction/diagnostics/STAGE2-ABI-AUDIT.md`.
   Он подтвердил 32-битный тип игровых часов и ранее исправленные wire-
   поля. В живом Lua `ObjectHash` обнаружено расхождение `Number → long`:
   большие ключи давали разные хеши на Windows и LP64. Преобразование
   сделано явно 32-битным, проверено на диагностическом Windows x86,
   Windows x64, Linux x86-64 и ARM64/QEMU; пять граничных ключей
   сохраняют значения после сохранения/загрузки. Побайтовый хеш всего
   Lua-состояния не стабилен даже между запусками одной ОС, поэтому
   здесь не заявляется кросс-совместимость сейвов. В 113 исходных скриптах
   `game.db` проверены числовые константы скомпилированных Lua-прототипов:
   18 записей, ни одной целой вне знакового 32-битного диапазона; это не
   исключает вычисляемые ключи. Отладочный аллокатор
   `Script/lmem.cpp` находится под `_DEBUG`, а
   `wCheckTooMuchCorpses.cpp` пока не вызывается из мира — их нельзя
   выдавать за проверенный живой дефект. После среза 3а для текущей
   границы игровых источников выполнен 3б (указатели, asm,
   выравнивание). В 3б обнаружена и исправлена разница между x86-asm
   `Min<float>`/`Max<float>` и переносимой веткой при NaN и `+0/-0`;
   пять побитных случаев совпали на диагностическом x86, Windows x64,
   Linux x86-64 и ARM64/QEMU. Ссылки на указатели/ASM и граница
   отложенных графических файлов разобраны в `STAGE2-ABI-AUDIT.md`;
   обзор источников 3б не выявил других незащищённых x86-инструкций в
   переносимом игровом контуре. Ветка Lua-формата `f` имеет старую
   ошибку varargs, но игровые вызовы с `f` не найдены; это отмечено
   как латентный случай, а не новая задача этапа 2. Срез 3б закрыт
   после адресных тестов и итоговой сборки; затем выполнен 3в (wire-формат
   и раскладка). Для 3в конечный порядок: (1) классифицировать прямые
   файловые потоки вне `CStructureSaver`; (2) проверить ширины,
   порядок байтов и раскладку реально читаемых игровых полей адресными
   тестами; (3) перечислить динамические состояния сейвов, которых не
   доказывает строгий обход 52 корней. Существующий 52/52-проход на
   полном зеркале ресурсов с нулём raw-типов — основа, но не замена
   этих проверок. Итоги межплатформенной матрицы приведены в пункте 4.
   Первый прямой файловый срез 3в перевёл длину `CDataStream`-строк и
   четырёхбайтный префикс `CNetCompressor` на явный little-endian, не
   меняя исходные байты; добавлены проверки точных префиксов и отказа
   от недопустимого размера. Адресные тесты прошли на диагностическом
   x86, Windows x64, Linux GCC x86-64 и ARM64/QEMU, `Game.exe` собран.
   Этот первый срез не закрывал весь 3в; последующие проверки прямых
   форматов и динамических состояний описаны ниже.
   Прямые вызовы потоков классифицированы в `STAGE2-ABI-AUDIT.md`:
   индекс 23 пакетов, заголовок сейва, строковые и сжатые префиксы —
   игровые входы; запись пакетов — инструментальная ветка; BMP/текстуры
   и медиапотоки — клиент/графика. Особый игровой `vector<bool>` флагов
   магазина теперь проверяет длину до выделения/сужения; его 30-байтный
   round-trip и побитный хеш совпали на x86, Windows x64, Linux x86-64
   и ARM64/QEMU. Четыре не-стартовых состояния (выстрел, слот, взрыв,
   граната из инвентаря) прошли save/load/продолжение на Windows x64,
   Linux x86-64 и ARM64/QEMU, на Linux под санитайзерами. Затем проведена
   инвентаризация *не покрытых этими тестами*
   динамических классов/состояний и проверка достигнутых игровых полей;
   52 стартовых корня нельзя выдавать за исчерпывающее покрытие сейвов.
   Первый фиксированный срез этой инвентаризации — четыре сохранения в
   `diagnostics/STAGE2-SAVE-TYPE-INVENTORY.md`: объединение 439 *живых*
   типов, 42 уникальных для одного из четырёх состояний; записи-
   надгробия учитываются отдельно. Список одного сейва
   (403 живых типа, 28 100 тел, включая 1 512 недействительных)
   совпал побайтно на диагностическом x86,
   Windows x64, Linux x86-64 и ARM64/QEMU. Среди уникальных — игровые
   состояния орудия, отступления ИИ, воксельного взрыва и CPU-анимации;
   визуальные/UI-классы отделены. Сравнение с шестью headless-сейвами показало,
   что они записаны после затухания взрыва: шесть классов активной
   воксельной волны/сетки там отсутствуют. Адресный тест 3в сохранил
   мир *во время* волны с шестью ранее отсутствовавшими типами, загрузил
   его и довёл взрыв до конца на диагностическом x86, Windows x64,
   Linux GCC x86-64 с санитайзерами и ARM64/QEMU с санитайзерами.
   Состояние у стационарного оружия уже проверено тем же адресным
   диагностическим тестом на диагностическом x86, Windows x64, Linux
   GCC x86-64 и ARM64/QEMU (с санитайзерами на Linux): после save/load
   сохраняются `CUnitStateUsingCannon`, связь героя с пушкой и ссылка на
   предмет оружия. Для завершения среза проверены классы отступления,
   критического состояния, Lua-позиции и CPU-анимации; их наблюдённая
   wire-раскладка уже совпала на четырёх целях, а `CAIRetreatLogic` и
   `CAPCritical` и `CLUAObjectPosition` также прошли runtime save/load
   на четырёх целях с санитайзерами. Оставшиеся `CAAdder`, `CARandom` и
   `CABoneFilter` являются presentation-анимационным графом (их тела и
   wire-раскладка уже совпали на четырёх целях); runtime-воспроизведение
   и визуальная проверка относятся к следующему графическому этапу.
   Кросс-загрузка GUI-сейва на
   Linux не является продуктовым требованием.

4. **Пройти финальную матрицу ядра.** После пунктов 1–3 выполнить

   сверяют значимые игровые значения с диагностическим x86 там, где
   есть исходный контракт. Проверить отделение ресурсов от сейвов и
   Unicode/регистр на применимых ОС. Результат: команды, хеши входов,
   журналы, известные ограничения и ноль необъяснённых падений/UB.
   Доказательства закрытия: Windows x64 прошёл 172/172 в предыдущей
   полной сборке; актуальный рабочий tree-прогон stage-2 набора (167
   тестов, без отложенного `NativeAnimatedLightResourceTests` и
   extended-наборов) прошёл 167/167 за 99.81 с. Linux
   Clang x86-64 прошёл 141/141; Linux GCC x86-64 прошёл 142/143,

## Явно вне этого checklist

SDL3/ввод/окно — этап 3; bgfx, частицы и анимированный свет как
изображение — этап 4; полный динамический паритет AI, боя и сценариев
